# Refactoring notes

- Both bank-message entry points use `BankMessageProcessor`. Matching, password filtering, parsing and duplicate checks run in one Room transaction. Notification failures are logged and service jobs are cancelled on destruction.
- Duplicate detection compares normalized message content for the same account within five seconds, including confirmed transactions. It does not merge messages on amount alone. Different or delayed message formats may still need manual review.
- `transactionReport` owns spending totals and category breakdowns. Shared repayments reduce the original expense in its original period; `netBetween` deliberately retains actual cash movements in the payment period.
- Transaction validation fetches the affected share family instead of all history. Period reports include linked repayments outside the period. Database version 13 adds indexes only; exported Room schemas and a migration test protect the version-12 upgrade path.
- Edit and confirmation dialogs close from successful persistence callbacks. Saving state prevents repeat submissions while preserving entered values after failure. Account creation and its sender mappings are atomic.
- Asset networking and persistence live in `AssetsViewModel`. Quote refresh updates price columns only, preserving edited quantities and avoiding recreation of deleted holdings. Transaction forms share `BankAccountPicker`.
- JSON backup format 2 includes pending/reviewed messages and settings. Legacy JSON and CSV remain readable. Unsupported future formats, duplicate IDs, invalid values and missing references are rejected before replacement. CSV remains a data export rather than a complete settings/review-history backup.
- Database restoration uses a transaction; preference restoration failures roll it back, and failed database commits restore the previous preferences. SQLite and SharedPreferences are separate stores, so abrupt process death between their commits cannot be fully atomic.
- `DecimalMoney` centralizes decimal ledger arithmetic, totals and budget estimates. Existing Toman amounts and JSON/database representations remain compatible; no currency-unit conversion is performed. Budget averages round to two decimal places with `HALF_UP`. Stored amounts still use `Double`/SQLite REAL, so extreme magnitudes retain that representation's precision limits. An integer-unit migration needs a separate currency precision contract.

Validation: unit/integration tests cover fractional payments, cross-period repayments, message deduplication and concurrent delivery, save callbacks/retry, quote updates, backup round trips and invalid restores, and a version-12 database upgrade with 1,000 transactions. Device delivery and live price endpoints require separate hardware/network verification.
